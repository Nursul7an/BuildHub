# Развёртывание

Есть два пути. **Свой сервер предпочтительнее** — не из-за цены, а потому
что фронтенд и API оказываются на одном домене, и вся возня с cookie между
разными сайтами отпадает сама.

| Путь | Где | Раздел |
|---|---|---|
| **Свой сервер** (Hetzner и любой другой) | всё в одном `docker compose` | §0 |
| Разнесённый | Vercel + Render/Fly | §1–§4 |

Сервер на Vercel не поднимается: там нет ни постоянного процесса под разбор
очереди событий, ни диска под фотографии, ни базы.

## 0. Свой сервер: Hetzner и подобные

Всё поднимается одной командой: PostgreSQL 16, сервер и Caddy, который
раздаёт фронтенд и переадресует `/api` внутрь. Наружу смотрит только Caddy.

### Что нужно заранее

- Сервер с Docker. Хватает **CX22** (2 vCPU, 4 ГБ) — под десяток объектов
  с запасом. Диск: 40 ГБ — это примерно 8–10 тысяч фотографий отчётов.
- **Домен**, A-записью направленный на IP сервера. Без него не будет
  сертификата, а без HTTPS браузер не отдаст камеру и геолокацию —
  отчёт с фото и геометкой сдать нельзя.
- Открытые порты 80 и 443.

### Запуск

```sh
git clone https://github.com/Nursul7an/BuildHub && cd BuildHub/deploy
cp .env.example .env
${EDITOR:-nano} .env          # домен, пароль базы, JWT_SECRET
docker compose up -d --build
```

Секреты сгенерировать:

```sh
openssl rand -base64 24   # POSTGRES_PASSWORD
openssl rand -hex 32      # JWT_SECRET и FILE_SIGNING_SECRET
```

Первая сборка занимает несколько минут. Дальше:

```sh
docker compose ps                       # все три службы running
curl https://ваш-домен/api/health       # {"ok":true}
curl https://ваш-домен/api/health/ready # база отвечает, где лежат файлы
```

Схема накатывается сама при старте контейнера — миграции версионированы,
повторный запуск ничего не делает.

Откройте домен в браузере: на экране входа будет ссылка
**«Зарегистрировать руководителя»** (см. §1 «Первый вход»).

### Обновление

```sh
cd BuildHub && git pull && cd deploy && docker compose up -d --build
```

### Резервные копии

`deploy/backup.sh` снимает дамп базы и архив фотографий, хранит 14 дней:

```sh
crontab -e
30 3 * * * /path/to/BuildHub/deploy/backup.sh >> /var/log/build-hub-backup.log 2>&1
```

Две честные оговорки. Это **снимок раз в сутки, а не восстановление на
момент времени**, которого требует ТЗ §3.1: потерять можно всё, что сделано
с последнего снимка. И копии лежат на том же сервере — пожар в дата-центре
уносит и то и другое, поэтому отвозите их наружу (Hetzner Storage Box,
rsync на другой хост).

### Почему один домен

Refresh-токен браузера лежит в httpOnly cookie с `SameSite=Lax`. Между
`*.vercel.app` и `*.onrender.com` браузер её не отправит — это разные
сайты, и вход перестал бы продлеваться молча. Здесь фронтенд и API на
одном домене, поэтому `VITE_API_BASE_URL`, `WEB_ORIGIN` и
`REFRESH_COOKIE_SAMESITE` задавать не нужно вовсе.

## 1. Разнесённый путь: сервер на Render

Нужен, только если фронтенд остаётся на Vercel. При развёртывании по §0
этот раздел и следующие три не нужны.

### Render

1. Render → **New** → **Blueprint**, указать этот репозиторий.
   `render.yaml` создаёт PostgreSQL 16, веб-сервис из `apps/server/Dockerfile`
   и диск на 10 ГБ под загрузки.
2. Секреты `JWT_SECRET`, `FILE_SIGNING_SECRET`, `METRICS_TOKEN` Render
   сгенерирует сам (`generateValue: true`).
3. Заполнить `WEB_ORIGIN` — адрес, выданный Vercel, например
   `https://build-hub.vercel.app`.

### Fly.io

Порядок команд — в комментарии в начале `fly.toml`.

### Что происходит при старте

Контейнер накатывает миграции (`prisma migrate deploy`) и запускает сервер.
Миграции версионированы, повторный запуск ничего не делает.

Сервер **откажется стартовать**, если в проде не задан `JWT_SECRET` или он
совпадает с отладочным значением из репозитория. Это намеренно: с известным
секретом токен любой роли подделывается за минуту.

### Первый вход

База поднимается пустой, и это нормально: на экране входа появится ссылка
**«Зарегистрировать руководителя»**. Первый директор заводит себя сам —
пароль задаёт свой, менять его при входе не потребуется.

Как только руководитель зарегистрирован, ссылка исчезает и регистрация
закрывается навсегда: дальше учётные записи выдаёт ПТО. Схема одноарендная,
отдельной компании у постороннего не будет, поэтому открытая регистрация
означала бы чужой директорский доступ к бюджетам и платежам.

Демонстрационные данные в проде не нужны. Для показа или разработки:

```sh
DATABASE_URL="<адрес базы>" npm run seed --workspace=@build-hub/server
```

Пароль учётных записей из фикстур — `buildhub2026`. **В проде эту команду
не запускайте**: она стирает данные и заводит вымышленных людей.

### Почему `npm ci --include=dev`

Vercel и подобные площадки выставляют `NODE_ENV=production` на время
установки, а npm при этом молча пропускает отладочные зависимости. Сборка
же стоит именно на них: `vite`, `typescript`, `tsc`. Без явного
`--include=dev` установка проходит успешно, а сборка падает на том, что
не находит `vite/client`, — и выглядит это как ошибка типов, а не как
недоустановленное дерево.

То же указано в `apps/server/Dockerfile`: полагаться на то, что
собирающая среда не выставит `NODE_ENV`, не стоит.

## 2. Фронтенд

Vercel собирает по `vercel.json` автоматически. После развёртывания сервера
нужно сделать ровно одно: вписать в `vercel.json` адрес, который выдал
Render, — тот, на который Vercel переадресует `/api/*`.

```json
{ "source": "/api/:path*", "destination": "https://ВАШ-СЕРВЕР.onrender.com/api/:path*" }
```

Затем закоммитить и запушить: Vercel пересоберёт сам.

Переменную `VITE_API_BASE_URL` задавать **не нужно** — фронтенд обращается
к `/api/...` на своём же адресе, а дальше работает переадресация. Так
браузер видит один сайт, и cookie с refresh-токеном не теряется
(подробности в §3).

Переменная остаётся на случай, когда сервер вызывают напрямую, минуя
переадресацию. Читается она **на этапе сборки**, а не в браузере: после
изменения нужен повторный деплой, иначе в бандле останется прежнее значение.

## 3. Cookie с refresh-токеном — решено переадресацией

Браузерный клиент хранит refresh-токен в httpOnly cookie: из localStorage
его унесла бы любая XSS, из httpOnly cookie — нет. Плата за это —
требование к доменам.

Cookie ставится с `SameSite=Lax`, и между `*.vercel.app` и `*.onrender.com`
браузер её просто не пошлёт: это **разные сайты**. Продление входа
перестало бы работать молча — человека выкидывало бы каждые пятнадцать
минут, обычно посреди сдачи отчёта.

**Решение: Vercel переадресует `/api/*` на сервер.** В `vercel.json`:

```json
{ "source": "/api/:path*", "destination": "https://build-hub-server.onrender.com/api/:path*" }
```

Замените адрес на свой — тот, что выдал Render.

Для браузера всё происходит на одном сайте, поэтому:

- cookie становится своей, `SameSite=Lax` работает;
- CORS не нужен вовсе — обращений на чужой адрес нет;
- запрет сторонних cookie (Safari режет их всегда, остальные постепенно)
  на вход не влияет;
- `VITE_API_BASE_URL` **не задаётся**: фронтенд обращается к своему же
  адресу. Переменная остаётся на случай, когда сервер вызывают напрямую.

### Если переадресацию не ставить

Тогда фронтенд ходит на чужой адрес, и нужны сразу три вещи:
`VITE_API_BASE_URL` с адресом сервера, `WEB_ORIGIN` с адресом фронтенда
и `REFRESH_COOKIE_SAMESITE=none`. Сервер не стартует, если `none` задан
без HTTPS, а обновление токена дополнительно требует заголовка
`x-build-hub-client: web` — он вынуждает предварительный запрос CORS,
и тот упирается в `WEB_ORIGIN`, закрывая подделку межсайтового запроса.

Этот путь рабочий, но в Safari сломается сразу, а в остальных браузерах
позже. Свой домен на обе части (`app.example.kg` и `api.example.kg`
с `REFRESH_COOKIE_DOMAIN=.example.kg`) — вариант не хуже переадресации.

### Если всё-таки не заработает

После входа клиент спрашивает `/api/auth/cookie-check`. Если cookie не
вернулась, на экране появится: «Браузер не сохранил сессию — вход
придётся повторять каждые 15 минут». Это сказано сразу, а не через
пятнадцать минут молчания, и по этой строке понятно, что чинить.

Мобильное приложение шлёт `client: "mobile"` при входе и получает
refresh-токен в теле ответа: cookie между запусками переживают не все
клиенты, а чужого JavaScript в приложении нет.

## 4. Проверка

```sh
curl https://<адрес сервера>/api/health         # процесс жив
curl https://<адрес сервера>/api/health/ready   # база отвечает, где лежат файлы
```

`/api/health/ready` возвращает 503, когда база недоступна, — по нему
балансировщик выводит неисправный экземпляр из ротации.

Поле `storage.persistent: false` означает, что том не подключён: фотографии
отчётов пропадут при перезапуске, а это доказательная база по скрытым работам.

## Что осталось за рамками

- **Файлы лежат на диске**, а не в S3/MinIO, как требует ТЗ §3.1. Драйвер
  повторяет контракт S3 (подпись + срок жизни ссылки), поэтому переключение
  будет заменой драйвера, а не переписыванием вызовов.
- **Очередь событий** разбирается таймером в процессе сервера, а не BullMQ
  (ТЗ §3.1). Контракт тот же — `DomainEvent` в той же транзакции, что и
  бизнес-запись, — но при нескольких экземплярах сервера воркер должен
  остаться в одном.
- **Резервные копии на момент времени** (ТЗ §3.1) — платный тариф Render
  или `fly postgres`; на минимальных тарифах их нет.
- **OpenTelemetry и Sentry** не подключены. Метрики отдаются в формате
  Prometheus на `/metrics`, цели по SLA из §11 считаются — см.
  `/api/v1/ops/sla`.
